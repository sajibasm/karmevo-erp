## Working with the spec

- Requirements carry IDs (e.g. `ARC-03`, `INV-04`, `AUTH-04`, `WFL-08`, `E2E-01`). Use them in backlog items, test names and a traceability matrix (requirement → implementation location → test evidence → status).
- Record assumptions; escalate decisions that change business scope, authentication, data ownership or compliance. Never invent commercial values (prices, grace days, quotas), tax/payroll rates, provider capabilities or bank statement formats. Mark these as blockers.
- Two major phases only. **Phase 1** covers the full ERP, admin, licensing, website/eCommerce, web POS, warehouse (USB/keyboard-wedge scanners) and mobile-ready API contracts, delivered as milestones P1.1–P1.9 (§22, §38, §46). **Phase 2** is one shared Flutter app for all tenants (staff + B2B buyer workspaces). Do not start production Flutter work before the Phase 1 exit gate.

## Fixed technology choices

- ERP backend: **FastAPI** (Python). Website server/backend: **Go**. Identity: **Keycloak**. Mobile: **Flutter/Dart**.
- Proposed defaults (confirm via ADR): modular monolith; PostgreSQL with module-based schemas (`platform`, `catalog`, `inventory`, `sales`, `purchasing`, `commerce`, `manufacturing`, `restaurant`, `finance`, `tax`, `people`, `service`, `documents`, `integration`); SQLAlchemy + Alembic; Celery + RabbitMQ; Redis; S3-compatible storage; React/TypeScript for ERP and POS UIs. Kafka is out of scope unless a later ADR justifies it. The website UI approach (Go-rendered vs React/Next.js) is still open. Pick one, not both.
- Pin dependencies after checking official docs for supported versions (OPS-07).

## Coding conventions

- **Python: PEP 8** (and PEP 257 docstrings), enforced by ruff with rules `E`, `W`, `N`, `D`, `F`, `I`, `B`, `UP` and a 99-character line limit. Use `snake_case` for functions, variables and modules, `PascalCase` for classes, and `UPPER_CASE` for constants. Imports are grouped stdlib → third-party → local. Run `ruff format` and `ruff check` before committing.
- **Database naming: CamelCase (ADR-0010).** Tables are plural PascalCase (`"SalesOrders"`). Columns are camelCase (`"orderStatus"`), and ids are spelled out (`"salesOrderId"`, never `id`). FK columns share the name of the referenced column, and generic words are qualified (`"companyName"`, not `name`). Schemas, databases and roles are lowercase. **Always double-quote table and column names in raw SQL.** ORM attributes stay snake_case and map explicitly: `company_name: Mapped[str] = mapped_column("companyName", ...)`.
- **API JSON: camelCase (ADR-0010).** All request/response models inherit `erp.shared.schemas.ApiSchema` (Pydantic `alias_generator=to_camel`, `populate_by_name=True`). Python fields stay snake_case and JSON keys are camelCase (`nextCursor`). Multi-word query params use `Query(alias="pageSize")`. Headers keep HTTP style (`X-Tenant-Id`).
- **Class-based code (ADR-0011).** There are no module-level functions in `erp/`; helpers are static/class methods (`Money.quantize`). Each module is layered Controller (`controller.py`, a `Controller` subclass owning an `APIRouter`) → Service (`service.py`; business rules and transactions; `provide` classmethod for FastAPI DI) → Repository (`repository.py`; all queries) → Model. Collaborators come in through `__init__`. Exceptions: Alembic `upgrade`/`downgrade`, the `__main__` guard, and pytest test functions/fixtures.
- **Open owner requirements** are tracked as `OWN-xx` rows at the end of `docs/plan/traceability.md` (e.g. OWN-01 restaurant self-service kiosks).

## Architecture invariants (span many modules)

- **Identity (ADR-0004 accepted):** one Keycloak per deployment with two realms shared by all tenants (`staff`, `customers`). Per-tenant Keycloak clients exist for redirect URIs and branding only; they never separate users.
- **Module ownership (ARC-01, ADR-0009):** every catalogue app is a package in `erp/modules/<key>/` with `module.py` (manifest + `depends_on`), `config.py`, `models.py`, `schemas.py`, `controller.py`, `service.py`, `repository.py`, `interface.py`, `utils.py` (all class-based, ADR-0011). Modules import each other only via `interface.py`. `erp/shared` holds cross-module building blocks and `erp/core` holds framework infrastructure; neither imports `erp.modules`. Each module owns its tables and rules. Cross-module writes go through interfaces. No universal CRUD service and no shared mutable tables. Register new modules in `InstalledModules.MANIFESTS` (`erp/module_catalog.py`); a manifest lists the module's `Controller` classes. A module's `depends_on` must follow `docs/plan/module-dependencies.md`, which is still a proposal; don't invent dependencies outside it. Tenants enable or disable non-core modules (`registry."TenantModules"`). `ApplicationFactory` guards every non-core controller's routes with `ModuleGuard`, and disabling never deletes data.
- **ERP is the authority (ARC-02):** pricing, tax, reservations, orders, stock, payroll and accounting live only in the ERP. Go and Flutter call ERP APIs and never write ERP tables or reimplement these rules.
- **Transactions + outbox (ARC-03, JOB-04):** atomic business changes happen in one DB transaction, with an outbox row written in the same transaction for any follow-up work. Consumers must be idempotent. Never assume the broker gives exactly-once delivery. Job status lives in PostgreSQL, not the broker.
- **Tenancy (TEN-01..03, DB-01/02, ADR-0002 accepted):** hierarchy is tenant → legal company → branch. Warehouses/locations form a separate stock hierarchy linked by explicit fulfilment mappings. **Each tenant has its own database** (`erp_t_<uuid hex>`). A central **registry DB** holds tenants/placement, identities and memberships. Resolve membership in the registry, then use `TenantDatabaseRouter.for_tenant()`. Inside tenant DBs, keep `tenant_id` columns, RLS and the FK to `platform.tenant_scope` on every tenant table. Cross-tenant data belongs only in the registry. Tenant migrations live in `migrations/tenant`, must be expand/contract compatible, and are applied by `python -m erp.cli upgrade-tenants`; never re-create a tenant DB that was migrated before. Tenant context comes from verified identity + membership, never a trusted header. Scope caches, jobs, files, search, exports, sockets and notifications by tenant. Account numbers are human-readable identifiers, not authorization.
- **Authorization order (AUTH-04/05):** active membership → licensed action → non-bypassable tenant/security/SoD rules → explicit denies (deny always wins) → group/user grants → default deny. Never merge conditions from different grants into a broader privilege. Every endpoint, query filter, field serializer, export, job and socket uses the same policy service. The UI is advisory only.
- **Licensing (§26):** kept separate from Keycloak and from ERP permissions. The control-plane DB is separate from business data. The runtime verifies signed grants using public keys only. Enforcement is a service called with (feature key, action, actor, scope, quota delta) that returns stable codes (`FEATURE_NOT_LICENSED`, `QUOTA_EXCEEDED`, `LICENSE_RESTRICTED`). Client-hosted operation must not depend on a live control plane.
- **Approvals (§36):** one shared workflow engine for all modules; don't build per-module engines. An approval covers a specific resource revision/hash, and material changes invalidate it. Approval state is tracked separately from domain execution state. Conditions use a restricted typed expression tree: no `eval`, raw SQL or dynamic method names.
- **Signing (§37):** a separate bounded capability connected to workflows by durable events. Original and completed bytes are immutable and hashed. Electronic signing is distinct from certificate-backed signatures.
- **Money/quantity (PLT-06):** decimals only with explicit rounding. UTC timestamps plus the business time zone.
- **Ledgers, not edits:** stock balances are projections of a stock movement ledger (INV-03). Financial corrections go through reversals/adjustments. Customer balances derive from posted receivables. Loyalty is an append-only ledger. Never hard-delete financial or stock records.
- **Snapshots:** freeze tax results, price rule versions, BOM/recipe versions, payroll inputs and landed-cost inputs on posted/released documents. Rule changes never rewrite history.
- **Idempotency everywhere:** webhooks, payment callbacks, POS/mobile sync, count approvals, dispatch, postings and bank reimports must dedupe via stable operation/event IDs plus DB constraints. Browser redirects never mark anything paid.
- **APIs (ARC-06):** versioned REST (`/api/v1/...`) with published OpenAPI, and defined conventions for pagination, errors, decimal serialization, idempotency keys and optimistic concurrency. Phase 1 must also publish mobile-ready contracts: account directory, capabilities, license status, device enrollment and sync push/pull with cursors/tombstones (FLT-02/03).
- **Same code for SaaS and client-hosted (OPS-01):** same container images and migrations, no customer forks. Bangladesh (BDT, Asia/Dhaka, Bangla/English) is the first localization package, versioned with golden tests. Don't hard-code rates.

## Definition of done for a feature (§35)

Migrations/constraints, real domain logic, API + OpenAPI, usable web UI where required, authorization and entitlement enforcement, audit, retry/concurrency handling, meaningful tests (map them to the §21 E2E gates where relevant), and operational notes. A disabled stub is not completion. Report implemented / verified / partial / blocked / deferred requirement IDs honestly.
